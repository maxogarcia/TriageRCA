# Resource Faults

## RES-CPU-001: CPU Hogging via Infinite Loop or Runaway Computation
- **Affected Services**: ts-travel-service, ts-order-service, ts-route-service, ts-seat-service
- **Fault Type**: Resource
- **Symptom**: Sustained CPU utilization at or near 100% on affected pod(s); response latency climbs sharply across dependent services; Prometheus `container_cpu_usage_seconds_total` rate pegs at the pod's CPU limit; `node_cpu_seconds_total{mode="idle"}` drops toward zero on the host; HTTP 504 Gateway Timeout or gRPC DEADLINE_EXCEEDED errors propagate upstream; Kubernetes liveness probes may start failing, triggering pod restarts (`kube_pod_container_status_restarts_total` increments)
- **Root Cause**: A fault-injected or buggy code path enters an infinite loop, unbounded recursive computation, or tight spin-wait without yielding. The thread (or all threads in a thread pool) saturate the CPU allocation, starving the event loop, health-check handlers, and garbage collection. In containerized environments the cgroup CPU quota is exhausted, causing kernel-level throttling (`container_cpu_cfs_throttled_seconds_total` rises) that makes the service appear frozen to callers
- **Diagnostic Steps**:
  1. Query `rate(container_cpu_usage_seconds_total{pod=~"<service>.*"}[2m])` and compare against `kube_pod_container_resource_limits{resource="cpu"}`; check `rate(container_cpu_cfs_throttled_periods_total[2m]) / rate(container_cpu_cfs_periods_total[2m])` for throttle ratio > 0.5; inspect `node_load1` on the host node
  2. Search application logs for absence of normal request-processing entries during the spike window (log silence indicates the event loop is blocked); inspect Jaeger traces for spans that never complete or show multi-second durations on a single service; look for repeated GC pause log entries (`gc_pause_seconds_sum` spike)
  3. `kubectl top pod -l app=<service> --containers` to confirm CPU consumption; `kubectl exec -it <pod> -- top -bn1 -H | head -20` to identify the hot thread; for JVM services: `kubectl exec -it <pod> -- jstack 1 | grep -A15 "RUNNABLE"` to capture the stack trace of spinning threads; `kubectl exec -it <pod> -- sh -c 'cat /sys/fs/cgroup/cpu.stat 2>/dev/null || cat /sys/fs/cgroup/cpu/cpu.stat'` to inspect cgroup v2 or v1 throttling counters
- **Remediation & Mitigation**: Immediate — remove the affected pod from traffic, roll back or disable the runaway code path, and restart the pod (`kubectl delete pod <pod>`) only after preserving any needed diagnostics; apply a CPU limit if missing and scale known-good replicas when the fault is isolated to a subset of pods. Long-term — add execution deadlines and iteration guards to compute-intensive paths; use bulkheads or circuit breakers to contain saturation; profile CPU usage with async-profiler or `perf` in staging; configure HPA only from validated workload signals because scaling identical faulty replicas can amplify an infinite-loop defect; alert on sustained CPU throttling and latency together

## RES-MEM-001: Memory Leak Leading to Heap Exhaustion and OOMKilled
- **Affected Services**: ts-basic-service, ts-ticketinfo-service, ts-food-map-service
- **Fault Type**: Resource
- **Symptom**: `container_memory_usage_bytes` climbs monotonically over minutes/hours without stabilizing; JVM `jvm_memory_used_bytes{area="heap"}` approaches `jvm_memory_max_bytes`; full GC frequency and duration increase (`jvm_gc_pause_seconds_sum`); eventually the pod is terminated with `OOMKilled` (ExitCode 137) visible in `kubectl describe pod`; `kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}` equals 1; dependent services see connection-reset errors during the kill window
- **Root Cause**: A fault-injected unbounded in-memory cache, leaked collection, or un-closed stream accumulates objects faster than garbage collection can reclaim them. The JVM heap fills to its `-Xmx` limit, triggering continuous full-GC cycles that consume CPU and stall request processing. When the container's RSS exceeds the Kubernetes memory limit, the Linux OOM killer terminates the process (SIGKILL, exit code 137). If no readiness probe catches the degraded state, traffic continues to route to the pod during the GC death spiral
- **Diagnostic Steps**:
  1. Query `container_memory_usage_bytes{pod=~"<service>.*"}` over 1h for a monotonic upward trend; check `jvm_memory_used_bytes{area="heap"}` and `jvm_gc_pause_seconds_count{gc="G1 Old Generation"}` for full-GC spikes; alert on `container_memory_usage_bytes / container_spec_memory_limit_bytes > 0.85`
  2. Search pod logs for `java.lang.OutOfMemoryError: Java heap space` or `GC overhead limit exceeded`; inspect Jaeger traces for request latency spikes that correlate with GC pauses; review application logs for cache-size or queue-depth warnings
  3. `kubectl describe pod <pod> | grep -A5 "Last State"` to confirm `OOMKilled` and exit code 137; `kubectl exec -it <pod> -- jcmd 1 GC.heap_info` for live heap information; `kubectl exec -it <pod> -- jmap -histo:live 1 | head -30` to identify dominant object types; `kubectl exec -it <pod> -- sh -c 'cat /sys/fs/cgroup/memory.peak 2>/dev/null || cat /sys/fs/cgroup/memory/memory.max_usage_in_bytes'` to inspect cgroup v2 or v1 peak usage
- **Remediation & Mitigation**: Immediate — remove the leaking pod from traffic, capture a heap histogram or dump if capacity permits, restart it, and scale known-good replicas to restore capacity; verify that memory requests and limits leave safe node headroom instead of arbitrarily tightening the limit. Long-term — fix the leak, bound caches with TTL and maximum-size eviction, close streams and connections deterministically, enable `-XX:+HeapDumpOnOutOfMemoryError` with a writable persistent dump path, use readiness checks based on the service's ability to serve rather than heap percentage alone, and alert when heap or container memory remains above 80% for five minutes

## RES-DISK-001: Disk I/O Saturation or Storage Volume Exhaustion
- **Affected Services**: ts-voucher-service, ts-admin-order-service, ts-news-service
- **Fault Type**: Resource
- **Symptom**: Disk write latency spikes (`node_disk_io_time_seconds_total` rate increases); application logs show `No space left on device` (ENOSPC) errors; database writes fail; Prometheus `node_filesystem_avail_bytes` approaches zero on the affected volume; `kubelet_volume_stats_available_bytes` for the PVC drops below threshold; pod may be evicted by kubelet when ephemeral storage exceeds the limit (`kube_pod_status_reason{reason="Evicted"}`)
- **Root Cause**: A fault-injected disk-stress workload, runaway logging (verbose debug logs under high traffic), unrotated log files, or temp-file accumulation fills the container's writable layer or mounted volume. Once the filesystem is full, all write operations fail — including application logs, database transactions, and temp-file creation — cascading into service unavailability. I/O saturation (even without full disk) causes write latency to spike as the I/O scheduler queues requests, making the service appear slow
- **Diagnostic Steps**:
  1. Check `node_filesystem_avail_bytes{mountpoint="/"}` and `kubelet_volume_stats_available_bytes{persistentvolumeclaim=~"<service>.*"}` in Prometheus; monitor `rate(node_disk_written_bytes_total[2m])` for abnormal write throughput; check `node_disk_io_time_weighted_seconds_total` for I/O saturation (utilization approaching 100%)
  2. Search application logs for `ENOSPC`, `No space left on device`, `IOException`, or database write-failure errors; check if log output stops abruptly (indicating the log sink itself is full); review systemd journal for kernel I/O error messages
  3. `kubectl exec -it <pod> -- df -h` to check filesystem usage; `kubectl exec -it <pod> -- du -sh /var/log/ /tmp/ /app/data/ 2>/dev/null | sort -rh | head -10` to find the largest directories; `kubectl exec -it <pod> -- ls -lhS /var/log/*.log | head -5` to identify oversized log files; `kubectl exec -it <pod> -- iostat -xm 1 3` (if available) to measure disk I/O utilization and await time
- **Remediation & Mitigation**: Immediate — stop or reduce the runaway writer, rotate and offload oversized logs, and remove only confirmed disposable temporary files; expand the PVC through the supported StorageClass workflow when capacity—not I/O saturation—is the constraint; reschedule the pod if the underlying node or volume is unhealthy. Long-term — configure log rotation with size and retention limits; set ephemeral-storage requests and limits; separate durable application data from logs and temporary files; use centralized log shipping with bounded local buffering; define alerts using both remaining bytes and percentage-free thresholds

## RES-SOCK-001: Socket Exhaustion from Connection Leaks (CLOSE_WAIT / TIME_WAIT)
- **Affected Services**: ts-travel-service, ts-inside-payment-service, ts-preserve-service, ts-food-service
- **Fault Type**: Resource
- **Symptom**: New outbound connections fail with `java.net.SocketException: Too many open files` or `Cannot assign requested address` (EADDRNOTAVAIL); Prometheus `process_open_fds` approaches `process_max_fds`; upstream callers receive connection-refused or timeout errors; `netstat`/`ss` shows thousands of sockets in `CLOSE_WAIT` or `TIME_WAIT` state; `node_sockstat_TCP_alloc` and `node_sockstat_TCP_tw` are abnormally high
- **Root Cause**: HTTP, gRPC, or database connections are opened without reliably closing or returning them to their pool, often because response bodies are not consumed or an exception bypasses cleanup. Application-side leaks commonly accumulate in `CLOSE_WAIT`, meaning the peer closed but the local process did not. Large `TIME_WAIT` counts usually indicate high short-lived connection churn rather than a leaked open socket; without connection reuse, that churn can still exhaust ephemeral ports. File-descriptor exhaustion or ephemeral-port exhaustion eventually prevents new dependency connections
- **Diagnostic Steps**:
  1. Check `process_open_fds{job="<service>"}` vs. `process_max_fds` in Prometheus; monitor `node_sockstat_TCP_alloc` and `node_sockstat_TCP_tw` on the host node; alert on `process_open_fds / process_max_fds > 0.8`
  2. Search application logs for `SocketException`, `Too many open files`, `Connection pool exhausted`, or `Cannot assign requested address`; inspect Jaeger traces for connection-setup spans that fail or time out; look for HTTP client warning logs about pool depletion
  3. `kubectl exec -it <pod> -- ss -tnp | awk '{print $1}' | sort | uniq -c | sort -rn` to count sockets by state; `kubectl exec -it <pod> -- ss -tnp state close-wait | wc -l` to count CLOSE_WAIT sockets; `kubectl exec -it <pod> -- ls /proc/1/fd | wc -l` to count open file descriptors; `kubectl exec -it <pod> -- cat /proc/sys/net/ipv4/ip_local_port_range` to check ephemeral port availability
- **Remediation & Mitigation**: Immediate — drain the affected pod, capture socket-state and file-descriptor evidence, restart it to release leaked descriptors, and temporarily disable the leaking request path or reduce traffic; raise descriptor limits only as a short-lived containment measure after confirming node capacity. Long-term — consume and close HTTP response bodies deterministically, return database connections to their pools, reuse clients and keep-alive connections, configure bounded pools with acquisition timeouts and idle eviction, instrument pool and descriptor metrics, and add alerts before exhaustion; avoid relying on TCP kernel tuning as a substitute for fixing `CLOSE_WAIT` leaks or connection churn
