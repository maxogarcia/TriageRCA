# Network Faults

## NET-DELAY-001: Injected Network Latency Causing Upstream Timeouts and Backpressure
- **Affected Services**: All / Ingress
- **Fault Type**: Network
- **Symptom**: End-to-end request latency increases by the magnitude of the injected delay (typically 200ms–5s per hop); Prometheus `http_request_duration_seconds{quantile="0.99"}` shifts upward on the target service and all its upstream callers; `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))` shows a step-change aligned with fault injection start; upstream services accumulate pending requests — thread-pool queue depth grows (`thread_pool_queue_size`), connection-pool active count rises (`http_client_pool_pending_requests`); callers eventually hit their timeout threshold and return HTTP 504 or gRPC DEADLINE_EXCEEDED; Kubernetes readiness probes with tight thresholds may start failing, removing the pod from endpoints
- **Root Cause**: Network latency is injected at the OS level (for example, `tc netem delay`) or through a service-mesh fault rule on a target traffic path. Packets traversing the affected queueing discipline or proxy are delayed before forwarding. A single impaired link adds its configured delay each time that link is traversed; delays accumulate across the call chain only when multiple hops or repeated calls traverse affected paths. Upstream services using synchronous blocking calls can exhaust bounded request or connection pools while waiting for the delayed dependency, propagating backpressure toward ingress
- **Diagnostic Steps**:
  1. Compare `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{service="<target>"}[5m]))` before and after the anomaly window; check `rate(http_requests_total{status="504"}[2m])` on upstream services; monitor `thread_pool_active_threads` and `http_client_pool_pending_requests` on callers for queue buildup; inspect `node_network_transmit_queue_length` on the host
  2. Inspect Jaeger traces for the affected call chain: the delayed service's span duration will show a constant additive latency; compare span start/end times between the caller and callee — the gap equals the injected delay; search application logs for `ReadTimeoutException`, `SocketTimeoutException`, or `DEADLINE_EXCEEDED` entries timestamped within the fault window
  3. `kubectl exec -it <target-pod> -- tc qdisc show dev eth0` to check for active `netem` rules; `kubectl exec -it <target-pod> -- ping -c5 <upstream-service-ip>` to measure actual RTT; `kubectl exec -it <caller-pod> -- curl -o /dev/null -s -w "time_connect: %{time_connect}\ntime_total: %{time_total}\n" http://<target-service>:8080/health` to measure end-to-end latency from the caller's perspective; `kubectl exec -it <target-pod> -- ss -ti | grep -A2 "rto:"` to inspect TCP retransmission timers
- **Remediation & Mitigation**: Immediate — remove the injected delay rule (`kubectl exec <pod> -- tc qdisc del dev eth0 root`); if using Istio fault injection, delete or update the VirtualService fault rule; shed noncritical traffic, open the circuit breaker, and scale healthy replicas if queues are already saturated; change timeouts only within the end-to-end deadline budget because longer timeouts can deepen backpressure. Long-term — define per-hop and end-to-end timeout budgets from measured latency distributions; retry only idempotent operations with jittered exponential backoff and a bounded retry budget; deploy circuit breakers and bulkheads; prefer asynchronous or non-blocking communication for latency-sensitive fan-out; alert when p99 latency exceeds twice the established baseline for two minutes

## NET-LOSS-001: Packet Loss Causing TCP Retransmissions and Inter-Service Communication Drops
- **Affected Services**: All / Ingress
- **Fault Type**: Network
- **Symptom**: Intermittent request failures — some requests succeed while others time out or return connection-reset errors; Prometheus `rate(node_network_transmit_drop_total[2m])` and `rate(node_network_receive_drop_total[2m])` may increase on the target node, while `rate(node_netstat_Tcp_RetransSegs[2m])` rises sharply; application-level error rates (`http_requests_total{status=~"5.."}`) increase with loss severity; `http_request_duration_seconds` becomes bimodal, with fast successes and retransmission-delayed responses; at high loss rates, TCP handshakes may time out entirely
- **Root Cause**: Packet loss is injected at the OS level (e.g., `tc netem loss 10%`) or via a service mesh fault-injection rule, causing a configured percentage of TCP segments to be silently dropped. The TCP stack detects missing segments via duplicate ACKs or retransmission timeout (RTO) and retransmits, adding 200ms–3s of delay per retransmission cycle. At moderate loss rates (5–15%) the effect is elevated latency and occasional timeouts; at high loss rates (>25%) TCP congestion control collapses the window, making the link effectively unusable. Three-way handshake SYN packets are also subject to loss, causing new connections to fail until the SYN is retransmitted (1–3s default RTO)
- **Diagnostic Steps**:
  1. Query `rate(node_netstat_Tcp_RetransSegs[2m])` and `rate(node_netstat_Tcp_OutSegs[2m])` in Prometheus; compute retransmission ratio: `retrans / out_segs > 0.01` indicates significant loss; check `rate(node_network_transmit_drop_total{device="eth0"}[2m])` on the target pod's node; monitor `http_request_duration_seconds` histogram for bimodal distribution (fast vs. retransmission-delayed buckets)
  2. Inspect Jaeger traces for requests with abnormally high span durations on a single hop that show no application-level processing time (the delay is in the network layer); search application logs for `Connection reset by peer`, `Broken pipe`, `Read timed out`, or `Connection timed out` errors with intermittent frequency; correlate error timestamps with `node_netstat_Tcp_RetransSegs` spikes
  3. `kubectl exec -it <target-pod> -- tc -s qdisc show dev eth0` to check active `netem loss` rules and qdisc drop statistics; `kubectl exec -it <caller-pod> -- ping -c 100 <target-service-ip> | tail -3` to measure packet loss percentage when ICMP is permitted; `kubectl exec -it <target-pod> -- cat /proc/net/snmp | grep Tcp` to read `RetransSegs` and `OutSegs`; `kubectl exec -it <target-pod> -- ss -ti dst <caller-ip>` to inspect per-connection retransmissions
- **Remediation & Mitigation**: Immediate — remove the injected loss rule (`kubectl exec <pod> -- tc qdisc del dev eth0 root`); if using Istio fault injection, remove the abort/delay percentage in the VirtualService; for persistent infrastructure-level loss, drain the node and reschedule pods to a healthy node (`kubectl cordon <node> && kubectl drain <node> --ignore-daemonsets`). Long-term — implement application-level retries with idempotency keys so retransmitted requests do not cause duplicate processing; deploy health-check-based outlier detection (Istio `outlierDetection` or Envoy `consecutive_5xx`) to eject pods with high error rates from the load-balancer pool; use TCP keepalives (`net.ipv4.tcp_keepalive_time=60, tcp_keepalive_intvl=10, tcp_keepalive_probes=3`) to detect dead connections quickly; configure connection pools with `maxRetries` and `connectTimeout` appropriate for the expected loss profile; set Prometheus alerting on `rate(node_netstat_Tcp_RetransSegs[5m]) / rate(node_netstat_Tcp_OutSegs[5m]) > 0.02`
