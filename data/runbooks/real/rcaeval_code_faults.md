# Code-Level Faults

## CODE-PARAM-001: Incorrect Parameters Passed in Inter-Service RPC/HTTP Calls
- **Affected Services**: ts-preserve-service, ts-security-service, ts-travel-plan-service, ts-route-service, ts-order-service, ts-station-service
- **Fault Type**: Code-level
- **Symptom**: Downstream service returns HTTP 400 Bad Request, 422 Unprocessable Entity, or a business-logic error with an error message indicating type mismatch or schema violation; Prometheus `http_requests_total{status="400",service="<downstream>"}` increases; callers receive unexpected error responses that propagate as HTTP 500 to the end user; Jaeger traces show the downstream span completing quickly with an error tag; partial data corruption if the downstream silently accepts the wrong-typed parameter (e.g., truncating a string-to-int cast)
- **Root Cause**: A fault-injected or buggy code path sends a request to a downstream service with an incorrect data type (e.g., `String` where `Integer` is expected), wrong field mapping (e.g., `orderId` sent as `trainNumber`), or a schema-incompatible payload (e.g., date in `MM/DD/YYYY` instead of `ISO 8601`). The downstream service's deserialization or validation layer rejects the malformed input, or worse, silently coerces it to a wrong value that corrupts downstream processing
- **Diagnostic Steps**:
  1. Check `http_requests_total{status="400",path=~"<downstream-endpoint>"}` and `http_requests_total{status="422"}` in Prometheus for the affected downstream service; correlate the spike with the caller service's `http_client_requests_total{status="400"}`
  2. Inspect the downstream service's logs for validation error messages (e.g., `JSON parse error: Cannot deserialize value of type 'Integer' from String`, `MethodArgumentTypeMismatchException`, `ConstraintViolationException`); in Jaeger traces, compare the request payload in the caller's outbound span with the downstream's inbound span metadata
  3. `kubectl logs -l app=<downstream-service> --tail=300 | grep -iE "400|Bad Request|parse error|type mismatch|deserializ"` to identify the rejected field; `kubectl exec -it <caller-pod> -- curl -v -X POST -H "Content-Type: application/json" -d '<reproduced-payload>' http://<downstream>:8080/<endpoint>` to reproduce the exact failure; diff the caller's request DTO against the downstream's expected DTO schema
- **Remediation & Mitigation**: Immediate — fix the parameter type or field mapping in the caller service's request construction code; redeploy the caller. Long-term — adopt shared API contract definitions (OpenAPI / Protobuf schemas) with compile-time client generation to prevent type drift; add request-payload validation in the caller before sending (fail-fast); implement contract tests (Pact / Spring Cloud Contract) between producer and consumer services in CI; add structured error logging on the downstream that includes the received vs. expected types for faster debugging

## CODE-PARAM-002: Missing Required Parameters in Inter-Service Requests
- **Affected Services**: ts-order-service, ts-contacts-service, ts-train-service, ts-config-service
- **Fault Type**: Code-level
- **Symptom**: Downstream service returns HTTP 400 Bad Request with a message indicating a required field is null or absent (e.g., `"field 'accountId' must not be null"`); Prometheus `http_requests_total{status="400",service="<downstream>"}` increases; if the downstream lacks proper validation, it may throw a `NullPointerException` resulting in HTTP 500; end users see a generic error or empty results for the affected operation
- **Root Cause**: A fault-injected or buggy code path omits a required field from the outgoing request payload or query parameters. The missing field may be due to a null variable that was never populated (e.g., a preceding service call failed silently and returned null), a conditional code branch that skips field assignment, or a DTO mapping that drops the field during serialization. The downstream service either rejects the request at its validation layer (clean failure) or proceeds with a null value, triggering a NullPointerException deeper in the processing logic
- **Diagnostic Steps**:
  1. Check `http_requests_total{status="400"}` and `http_requests_total{status="500"}` on the downstream service in Prometheus; filter by endpoint path to isolate the affected operation; check caller-side `http_client_requests_total{status="400"}` for the same time window
  2. Search downstream service logs for `MethodArgumentNotValidException`, `MissingServletRequestParameterException`, `NullPointerException`, or `Required field .* is missing` messages; inspect Jaeger traces for the failing request — check the caller's outbound span attributes for null or absent fields; look for a preceding span in the caller that returns null (the source of the missing value)
  3. `kubectl logs -l app=<downstream> --tail=300 | grep -iE "required|missing|null|NotValid|400"` to identify which field is missing; `kubectl exec -it <caller-pod> -- curl -v -X POST -H "Content-Type: application/json" -d '{}' http://<downstream>:8080/<endpoint>` to test with an empty payload and read the validation error response; compare the request body against the `@NotNull` / `@Valid` annotations in the downstream's DTO class
- **Remediation & Mitigation**: Immediate — fix the caller code to populate the required field; if the field depends on an upstream call, add a null-check with a meaningful error before proceeding. Long-term — add `@NotNull` / `@Valid` bean validation annotations on all request DTOs in every downstream service so missing fields produce a clear 400 instead of a 500; implement defensive coding in callers: validate all required fields are non-null before sending the request; add integration tests that verify every required field combination; use OpenAPI `required` field specs to auto-generate client-side validation

## CODE-FUNC-001: Missing Function Call Skipping a Required Processing Step
- **Affected Services**: ts-preserve-service, ts-cancel-service, ts-rebooking-service, ts-execute-service
- **Fault Type**: Code-level
- **Symptom**: The overall operation appears to succeed (HTTP 200) but a side-effect is missing — a downstream service was never notified, a database record was not updated, or a message was never published to the queue; users experience inconsistent state (e.g., ticket reserved but seat not locked, order cancelled but payment not refunded); Prometheus shows no errors on the affected service but downstream metrics such as `notification_sent_total` or `payment_refund_total` flat-line during the fault window; Jaeger traces for the operation show fewer spans than expected — the missing call's span is absent
- **Root Cause**: A fault-injected or buggy code path skips an essential function call in a multi-step workflow. The missing call may be a downstream RPC (e.g., notifying the payment service to issue a refund), a local method invocation (e.g., updating inventory), or a message publish (e.g., emitting an event to Kafka). The omission can be due to a removed or commented-out line, a conditional branch that evaluates incorrectly, or an early return that bypasses the remaining steps. Because the HTTP response is still 200 OK, the issue is invisible to simple status-code monitoring
- **Diagnostic Steps**:
  1. Compare expected vs. actual call rates on the downstream service: `rate(http_requests_total{service="<expected-downstream>"}[5m])` should correlate with the upstream's operation rate; a drop to zero or a significant gap indicates the call is not being made; check `message_published_total{topic="<expected-topic>"}` for event-driven steps
  2. Inspect Jaeger traces for the affected operation: compare the span tree against the expected sequence diagram — the missing call will be absent as a child span; search the caller's logs for the function or RPC endpoint name that should appear but does not; diff the current code against the last known-good version to identify removed or bypassed lines
  3. `kubectl logs -l app=<service> --tail=500 | grep -c "<expected-function-or-endpoint>"` to count invocations (expect > 0); `kubectl exec -it <downstream-pod> -- curl localhost:8080/actuator/metrics/http.server.requests?tag=uri:<expected-endpoint>` to verify zero inbound requests; `kubectl logs -l app=<downstream> --tail=300 | grep "<expected-request-pattern>"` to confirm absence
- **Remediation & Mitigation**: Immediate — restore the missing function call in the source code and redeploy; manually trigger the skipped step for affected records (e.g., issue refunds for orders that were cancelled without refund). Long-term — adopt a saga/workflow orchestrator (Temporal, Camunda) that enforces step completion and compensates on failure; add end-to-end integration tests that assert all side-effects of each operation; implement a reconciliation job that detects and repairs inconsistent states (e.g., cancelled orders with no corresponding refund record); instrument each workflow step as a named span so trace-based monitoring can alert on missing spans

## CODE-RET-001: Incorrect Return Value with HTTP 200 OK (Corrupted or Null Payload)
- **Affected Services**: ts-ticketinfo-service, ts-food-service, ts-station-service, ts-price-service
- **Fault Type**: Code-level
- **Symptom**: HTTP 200 OK is returned but the response body contains null fields, empty objects, wrong values, or a structurally valid but semantically incorrect payload; callers process the bad data without error, leading to silent data corruption downstream — wrong prices displayed, null names rendered as "null" in the UI, or incorrect calculations; Prometheus error-rate metrics remain flat (status is 200), making the fault invisible to standard alerting; `data_integrity_check_failures_total` (if instrumented) increments; end users report wrong information but the system shows no errors
- **Root Cause**: A fault-injected or buggy code path returns a response with a 200 status code but the payload is corrupted — a field is populated with a hardcoded wrong value, a null is returned where a valid object is expected, a default/fallback value is used instead of the actual computation result, or the serialization produces a structurally valid JSON with semantically wrong content. Because the HTTP status is 200, standard error-rate monitoring and circuit breakers do not trigger. Callers trust the 200 and propagate the bad data
- **Diagnostic Steps**:
  1. Standard error-rate metrics will NOT catch this fault — check content-level metrics if instrumented: `data_integrity_check_failures_total`, `response_null_field_total{field="<name>"}`, or `price_deviation_ratio` in Prometheus; compare actual response values against expected ranges using custom metric recording rules; monitor downstream effects: `ui_render_error_total{type="null_display"}` or user-reported defect rate
  2. Inspect Jaeger trace span attributes or logs for the returned payload on the affected service; compare actual values against the database source of truth; search for `null` or `0` values in fields that should be populated; review recent code changes or fault-injection configuration for hardcoded return values or early returns bypassing computation
  3. `kubectl exec -it <pod> -- curl -s localhost:8080/<endpoint>/<known-valid-id> | python3 -m json.tool` to manually inspect the response payload; `kubectl exec -it <pod> -- curl -s localhost:8080/<endpoint>/<known-valid-id> | python3 -c "import sys,json; d=json.load(sys.stdin); assert d.get('price') is not None, 'price is null'"` to run a spot-check assertion; compare the API response against a direct database query: `kubectl exec -it <db-pod> -- mysql -e "SELECT * FROM <table> WHERE id='<id>'"` to verify the source data is correct
- **Remediation & Mitigation**: Immediate — fix the return-value logic in the affected service and redeploy; identify and repair any downstream data that was corrupted by the bad payloads. Long-term — implement response-body validation in callers: assert that critical fields are non-null and within expected ranges before processing; add content-based health checks that periodically query known-good IDs and validate the response against expected values; deploy response-schema validation middleware (JSON Schema or OpenAPI response validation) in staging/canary that logs deviations; instrument semantic metrics (e.g., `price_returned_value` histogram) that enable anomaly detection on the data itself, not just the HTTP status

## CODE-EXC-001: Unhandled Exception Causing HTTP 500 Errors and Worker Instability
- **Affected Services**: ts-auth-service, ts-order-other-service, ts-admin-basic-info-service, ts-notification-service
- **Fault Type**: Code-level
- **Symptom**: HTTP 500 Internal Server Error responses spike, and callers may receive an unstructured error or exposed stack trace when error serialization is misconfigured; Prometheus `http_requests_total{status="500",service="<service>"}` increases; repeated failures can raise CPU and log volume and saturate request queues; exceptions that escape custom asynchronous executors or scheduled workers can terminate those worker tasks and cause background processing to stall; `kube_pod_container_status_restarts_total` may increase if the exception crashes the main process or causes liveness probes to fail
- **Root Cause**: A code path throws a runtime exception (for example, `NullPointerException`, `ClassCastException`, `ArrayIndexOutOfBoundsException`, or `NumberFormatException`) without an appropriate local recovery boundary or global exception handler. Servlet containers such as Tomcat normally catch request-handler exceptions and return HTTP 500 while retaining or replacing the request worker; however, exceptions that escape custom executor, scheduler, or event-consumer boundaries can terminate a worker task or thread. Without centralized error handling, callers receive inconsistent responses and internal details may be exposed
- **Diagnostic Steps**:
  1. Check `rate(http_requests_total{status="500",service="<service>"}[2m])` in Prometheus; monitor `thread_pool_active_threads`, `thread_pool_queue_size`, executor task-failure counters, and `jvm_threads_live_threads`; correlate error-rate spikes with pod restarts and liveness failures
  2. Search service logs for the first full stack trace and identify the exception class, originating line, request ID, and execution context; inspect Jaeger traces for spans with `error=true` and determine whether the failure occurred in a request handler, scheduled job, message consumer, or custom executor
  3. `kubectl logs -l app=<service> --tail=500 | grep -B2 -A10 "Exception\|at.*\.java:"` to capture stack traces; `kubectl exec -it <pod> -- jcmd 1 Thread.print | grep -E "http-nio|pool-|scheduler"` to inspect request and background workers; `kubectl exec -it <pod> -- curl -i localhost:8080/<endpoint-that-triggers-exception>` to verify the status code and confirm that the response does not expose a stack trace
- **Remediation & Mitigation**: Immediate — roll back or disable the failing code path, then add a narrowly scoped recovery boundary that maps the known exception to a structured, sanitized response or retryable job failure; restart only workers that have stalled and redeploy the corrected service. Long-term — implement centralized exception mapping (`@ControllerAdvice` in Spring Boot or equivalent middleware), instrument executor and consumer failure counters, configure supervised worker restart behavior, preserve request and trace IDs in error logs, add tests for null inputs and edge cases, and run static analysis such as SpotBugs or Error Prone in CI
