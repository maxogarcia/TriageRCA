# Online Boutique Resource Faults

## OB-RES-MEM-001: Recommendation Service Memory Leak and OOMKill
- **Affected Services**: recommendationservice, productcatalogservice, frontend
- **Fault Type**: Resource
- **Symptom**: Recommendations become intermittently unavailable or disappear from product pages; frontend requests may return HTTP 500/503 while product details still load; `container_memory_working_set_bytes{namespace="<namespace>",pod=~"recommendationservice-.*"}` rises monotonically toward the limit; Python process RSS grows, restarts increase, and `kube_pod_container_status_last_terminated_reason{namespace="<namespace>",pod=~"recommendationservice-.*",reason="OOMKilled"}` becomes 1; traces show failed or reset gRPC calls from frontend to recommendationservice
- **Root Cause**: The Python recommendationservice retains product results, request objects, trace data, or an unbounded cache across requests. Its resident set grows until the container exceeds its cgroup memory limit and is killed, interrupting the recommendationservice-to-productcatalogservice lookup and resetting in-flight gRPC calls
- **Diagnostic Steps**:
  1. In Prometheus, graph `container_memory_working_set_bytes{namespace="<namespace>",pod=~"recommendationservice-.*"}` and `process_resident_memory_bytes{job="recommendationservice"}` over at least one hour, compare them with `kube_pod_container_resource_limits{namespace="<namespace>",pod=~"recommendationservice-.*",resource="memory"}`, and check `increase(kube_pod_container_status_restarts_total{namespace="<namespace>",pod=~"recommendationservice-.*"}[1h])`
  2. Inspect Jaeger traces for frontend → recommendationservice → productcatalogservice and identify whether failures begin inside recommendationservice; correlate trace IDs with logs containing `MemoryError`, allocation failures, worker exits, or connection resets
  3. Confirm termination and limits with `kubectl describe pod -n <namespace> <recommendation-pod>` and `kubectl get pod -n <namespace> <recommendation-pod> -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}{" limit="}{.spec.containers[*].resources.limits.memory}{"\n"}'`
  4. Before restarting and only when capacity permits, attach an authorized diagnostic container with `kubectl debug -n <namespace> pod/<recommendation-pod> -it --image=<approved-python-debug-image> --target=server --profile=general`; capture bounded process evidence and read `cat /sys/fs/cgroup/memory.current 2>/dev/null || cat /sys/fs/cgroup/memory/memory.usage_in_bytes` for cgroup v2 or v1
- **Remediation & Mitigation**: Immediate — drain the leaking recommendationservice pod, capture safe memory evidence, restart it, and keep frontend traffic on healthy replicas; roll back the correlated revision or disable the leaking recommendation path rather than merely raising the limit. Long-term — fix retained references, bound caches by size and TTL, stream or paginate catalog results, add Python allocation profiling and soak tests, set measured requests and limits, and alert on sustained memory slope before OOMKill
