# Sock Shop Network Faults

## SS-NET-AMQP-001: RabbitMQ Connectivity Failure Disrupts Shipping Tasks
- **Affected Services**: shipping, queue-master, rabbitmq
- **Fault Type**: Network
- **Symptom**: If shipping cannot publish, its HTTP endpoint can still accept the shipment while logging that it could not add the task to the queue, so no RabbitMQ backlog is guaranteed and work may be lost. If queue-master alone is disconnected, `rabbitmq_queue_messages_ready{queue="shipping-task"}` rises while consumers fall, and queued shipment tasks remain unprocessed
- **Root Cause**: DNS failure, a blocked TCP 5672 path, packet loss, or latency interrupts one of two distinct AMQP connections: shipping publishes a task to RabbitMQ's `shipping-task` queue, and queue-master consumes that queue. The documented queue is non-durable, and the current shipping code catches publish exceptions and still returns the shipment, so the runbook must not assume publisher confirms, durable storage, or automatic replay
- **Diagnostic Steps**:
  1. Query `rabbitmq_queue_messages_ready{queue="shipping-task"}`, `rabbitmq_queue_messages_unacknowledged{queue="shipping-task"}`, `rabbitmq_queue_consumers{queue="shipping-task"}`, and `rabbitmq_connections`; distinguish a publisher-side outage with no queue growth from a consumer-side outage with ready messages accumulating
  2. Review `kubectl logs deployment/shipping -n <namespace> --since=30m` for `Unable to add to queue` or AMQP connection errors and `kubectl logs deployment/queue-master -n <namespace> --since=30m` for consumer connection or delivery failures; correlate the timestamps with RabbitMQ logs and the `shipping-rabbitmq` and `queue-master-rabbitmq` health results
  3. Verify `kubectl get service rabbitmq -n <namespace>` and `kubectl get endpointslice -n <namespace> -l kubernetes.io/service-name=rabbitmq`; from an authorized ephemeral debug container attached to the affected application pod, test DNS and TCP connectivity to `rabbitmq:5672`, then inspect only the NetworkPolicies and fault-injection resources governing that path
- **Remediation & Mitigation**: Immediate — restore RabbitMQ endpoints and TCP 5672 reachability, remove confirmed fault-injection rules, and restart only connections that do not recover. If queue-master alone failed, let it drain the existing `shipping-task` backlog at a controlled rate; if shipping failed to publish, reconstruct missing tasks from authoritative completed-order records only after making reprocessing idempotent. Long-term — explicitly redesign the queue as durable with persistent messages, publisher confirms, defined acknowledgements, dead-letter handling, bounded reconnect backoff, and idempotent task processing; add separate publisher- and consumer-path alerts and regularly test AMQP disconnect recovery
