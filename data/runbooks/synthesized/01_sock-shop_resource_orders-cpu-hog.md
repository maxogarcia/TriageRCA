# Sock Shop Resource Faults

## SS-RES-CPU-001: Orders Service CPU Hogging
- **Affected Services**: orders
- **Fault Type**: Resource
- **Symptom**: Java orders pods sustain CPU usage near their cgroup limit; order submission p95/p99 latency rises; HTTP 502/503/504 responses may propagate through front-end; CFS throttling and runnable application threads increase while catalogue, carts, orders-db, payment, and shipping may remain healthy
- **Root Cause**: A tight loop, runaway serialization, inefficient total calculation, or unbounded processing of an oversized request consumes the orders container's CPU. Cgroup throttling then delays HTTP handlers, MongoDB operations, and downstream calls, causing queueing and timeouts even though the pod remains running. The precise hot path must be established from repeated stack or profile evidence
- **Diagnostic Steps**:
  1. Compare `sum by (pod) (rate(container_cpu_usage_seconds_total{pod=~"orders-.*",container="orders"}[5m]))` with `sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{pod=~"orders-.*",container="orders"}[5m])) / sum by (pod) (rate(container_cpu_cfs_periods_total{pod=~"orders-.*",container="orders"}[5m]))`; correlate saturation with `sum(rate(http_request_duration_seconds_count{pod=~"orders-.*"}[5m]))` rather than assuming legitimate load
  2. Inspect a slow front-end-to-orders trace and separate orders self-time from MongoDB or downstream wait time; review `kubectl logs deployment/orders -n <namespace> --since=20m` for timeouts, GC pressure, and the affected request path, while avoiding customer payloads or credentials
  3. Run `kubectl top pods -n <namespace> -l name=orders --containers` and inspect limits with `kubectl get deployment orders -n <namespace> -o jsonpath='{.spec.template.spec.containers[?(@.name=="orders")].resources}'`. Because the orders image is JRE-based, do not assume `jcmd` exists in it; when authorized, attach a compatible JDK ephemeral debug container with `kubectl debug -n <namespace> pod/<orders-pod> -it --image=eclipse-temurin:8-jdk --target=orders`, identify the actual orders Java PID, and collect several `jcmd <java-pid> Thread.print` samples to find persistently runnable stacks
- **Remediation & Mitigation**: Immediate — remove the hot pod from traffic, preserve repeated thread evidence, roll back or feature-disable the correlated path, and scale only known-good replicas if orders-db and downstream services have headroom. Long-term — profile and bound the confirmed hot path, reject pathological payload sizes, add CPU regression tests, size requests and limits from observed demand, and alert on throttling plus order latency rather than CPU alone
