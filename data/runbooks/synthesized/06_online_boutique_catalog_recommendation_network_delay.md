# Online Boutique Network Faults

## OB-NET-DELAY-001: Catalog Path Latency Delays Product and Recommendation Responses
- **Affected Services**: frontend, productcatalogservice, recommendationservice
- **Fault Type**: Network
- **Symptom**: The home page and product-detail pages load slowly, recommendation panels time out, and frontend may return HTTP 504; p99 gRPC client latency rises for frontend → productcatalogservice and recommendationservice → productcatalogservice; traces show a nearly constant added delay on catalog calls, with `DEADLINE_EXCEEDED` once the caller budget is exceeded, while CPU and memory on all three services remain near baseline
- **Root Cause**: A `tc netem` rule, service-mesh fault rule, or degraded network path adds latency to traffic reaching productcatalogservice. Both frontend and recommendationservice depend on its gRPC API, so the delay affects direct catalog rendering and the nested recommendation lookup, lengthening the critical path and causing caller queues to build
- **Diagnostic Steps**:
  1. In Prometheus, compare `histogram_quantile(0.99, sum by (le, grpc_service) (rate(grpc_client_handling_seconds_bucket{job=~"frontend|recommendationservice",grpc_service=~".*ProductCatalog.*"}[5m])))` before and during the incident; check `rate(grpc_client_handled_total{job=~"frontend|recommendationservice",grpc_code="DEADLINE_EXCEEDED"}[5m])` and confirm local CPU/memory are not saturated
  2. Inspect Jaeger traces for frontend → productcatalogservice and frontend → recommendationservice → productcatalogservice; a similar additive gap before catalog responses, without elevated catalog application self-time, indicates path delay rather than slow catalog code
  3. Use authorized ephemeral containers because the application images may lack a shell and diagnostic binaries: `kubectl debug -n <namespace> pod/<frontend-pod> -it --image=<approved-network-debug-image> --target=server --profile=general` and the equivalent command for `<recommendation-pod>`; from each shared network namespace, time `grpc_health_probe -addr=productcatalogservice:3550`, then inspect the catalog pod's qdisc with the same method and `tc -s qdisc show dev eth0`
  4. Review service-mesh configuration and endpoint placement with `kubectl get virtualservice,destinationrule -n <namespace> -o yaml` and `kubectl get pods -n <namespace> -l app=productcatalogservice -o wide`
- **Remediation & Mitigation**: Immediate — remove the verified delay rule or route traffic to healthy catalog endpoints, shed noncritical recommendation work if queues are growing, and keep per-hop timeouts within the end-to-end request budget rather than extending them blindly. Long-term — define measured gRPC deadline budgets, add circuit breaking and bounded queues, cache safe catalog reads where appropriate, test delayed catalog dependencies in staging, and alert on catalog-path p99 latency together with `DEADLINE_EXCEEDED`
