# Online Boutique Network Faults

## OB-NET-LOSS-002: Packet Loss in the Checkout Payment-Shipping-Email Dependency Chain
- **Affected Services**: checkoutservice, paymentservice, shippingservice, emailservice
- **Fault Type**: Network
- **Symptom**: Checkout completes inconsistently or fails with HTTP 500/503/504; checkoutservice reports gRPC `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `connection reset by peer`, or `broken pipe` for paymentservice, shippingservice, or emailservice; TCP retransmission ratio rises; traces contain a failed or unusually long dependency span, and retries may produce duplicate payment attempts or repeated confirmation email unless protected
- **Root Cause**: Packet loss on one or more checkoutservice dependency paths drops TCP segments during the checkout workflow. TCP retransmissions consume per-call deadlines, and a lost response can leave checkoutservice uncertain whether payment or shipping work completed, creating partial-completion risk if it retries a non-idempotent operation
- **Diagnostic Steps**:
  1. In Prometheus, query `rate(node_netstat_Tcp_RetransSegs[5m]) / rate(node_netstat_Tcp_OutSegs[5m])` on checkout and dependency nodes, then break down `rate(grpc_client_handled_total{job="checkoutservice",grpc_service=~".*(Payment|Shipping|Email).*",grpc_code=~"UNAVAILABLE|DEADLINE_EXCEEDED"}[5m])` by `grpc_service` to identify the impaired edge
  2. Inspect failed checkout traces in call order and compare client and server spans: a client error with no server span suggests pre-delivery loss, while a successful payment server span followed by a lost client response indicates an unknown-outcome transaction that must be reconciled before retrying; correlate the trace ID with checkoutservice and dependency logs for `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `connection reset`, or duplicate-operation warnings
  3. Because the checkoutservice image may not contain a shell or network tools, attach an authorized ephemeral container with `kubectl debug -n <namespace> pod/<checkout-pod> -it --image=<approved-network-debug-image> --target=server --profile=general`; from the shared pod network namespace, run `tc -s qdisc show dev eth0`, `ss -ti`, `grpc_health_probe -addr=paymentservice:50051`, `grpc_health_probe -addr=shippingservice:50051`, and `grpc_health_probe -addr=emailservice:5000`
  4. Correlate endpoint and node scope using `kubectl get pods -n <namespace> -l 'app in (checkoutservice,paymentservice,shippingservice,emailservice)' -o wide` and `kubectl get endpointslice -n <namespace> -o wide | grep -E 'paymentservice|shippingservice|emailservice'`
- **Remediation & Mitigation**: Immediate — remove the verified loss rule or route away from the impaired endpoint, stop blind payment retries, and reconcile transaction status before resuming checkout; retry email notification separately only when its operation is idempotent. Long-term — require stable idempotency keys for payment and shipment creation, model checkout as a recoverable state machine with reconciliation or compensating actions, use bounded jittered retries and circuit breakers per dependency, add outlier detection, and alert on per-edge gRPC failures plus TCP retransmissions
