# Online Boutique Resource Faults

## OB-RES-MEM-002: Cart Service Memory Growth Exhausts the Pod
- **Affected Services**: cartservice, frontend, checkoutservice, redis-cart
- **Fault Type**: Resource
- **Symptom**: Add-to-cart, get-cart, and checkout operations become slow or return HTTP 500/503; `container_memory_working_set_bytes{namespace="<namespace>",pod=~"cartservice-.*"}` climbs without returning to baseline; .NET heap size and garbage-collection pause metrics rise when exported; pod restarts increase and the last termination reason becomes `OOMKilled`; traces show frontend or checkoutservice gRPC calls failing at cartservice while Redis latency remains normal
- **Root Cause**: The C# cartservice retains request, cart, serialization, or Redis-client objects in an unbounded in-process collection, or allocates faster than the .NET garbage collector can reclaim memory. The container crosses its cgroup memory limit and is OOM-killed even though the Redis-backed cart data store is healthy
- **Diagnostic Steps**:
  1. In Prometheus, graph `container_memory_working_set_bytes{namespace="<namespace>",pod=~"cartservice-.*"}` against `kube_pod_container_resource_limits{namespace="<namespace>",pod=~"cartservice-.*",resource="memory"}` and query `increase(kube_pod_container_status_restarts_total{namespace="<namespace>",pod=~"cartservice-.*"}[1h])`; if .NET metrics are exposed, inspect `process_runtime_dotnet_gc_heap_size_bytes` and GC collection rates
  2. Compare traces for frontend → cartservice and checkoutservice → cartservice with the cartservice → redis-cart span; high cartservice self-time with normal Redis spans points to local allocation or GC pressure, while logs may show `OutOfMemoryException`, long GC pauses, or worker termination
  3. Confirm the kill reason and configured limit with `kubectl describe pod -n <namespace> <cart-pod>` and `kubectl get pod -n <namespace> <cart-pod> -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}{" limit="}{.spec.containers[*].resources.limits.memory}{"\n"}'`
  4. Do not assume the hardened cartservice image contains a shell or .NET tools; if an approved diagnostic image and process-namespace sharing are available, run `kubectl debug -n <namespace> pod/<cart-pod> -it --image=<approved-dotnet-debug-image> --target=server --profile=general` and capture a bounded heap/runtime snapshot, otherwise record `/proc/1/status`, cgroup memory counters, prior container logs, and restart history before recovery
- **Remediation & Mitigation**: Immediate — remove the leaking cartservice pod from traffic, capture safe diagnostics, restart it, and roll back the suspected version while keeping redis-cart intact so durable cart data is preserved; scale only healthy revisions if load requires it. Long-term — fix retained-object and client-lifecycle defects, bound all local caches, tune .NET heap behavior within the container limit, run memory soak tests for add/get/empty-cart flows, set evidence-based requests and limits, and alert on memory-growth slope plus GC pressure
