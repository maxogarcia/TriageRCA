# Sock Shop Resource Faults

## SS-RES-CPU-002: Catalogue Service CPU Saturation
- **Affected Services**: catalogue
- **Fault Type**: Resource
- **Symptom**: Go catalogue pods consume sustained CPU near their limit; product-list and search latency rises; front-end pages become slow or return HTTP 502/504; CFS throttling increases; traces show long catalogue processing time even when catalogue-db query time remains normal
- **Root Cause**: An injected or regressed CPU-bound path in catalogue—such as inefficient filtering, repeated serialization, or unbounded result processing—consumes the container's CPU. Cgroup throttling then delays request goroutines and MySQL response handling, so the database can appear implicated even when its own latency is normal. A specific regular-expression or cardinality mechanism must be proven from the deployed code and profile rather than assumed
- **Diagnostic Steps**:
  1. Query `sum by (pod) (rate(container_cpu_usage_seconds_total{pod=~"catalogue-.*",container="catalogue"}[5m]))` and `sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{pod=~"catalogue-.*",container="catalogue"}[5m])) / sum by (pod) (rate(container_cpu_cfs_periods_total{pod=~"catalogue-.*",container="catalogue"}[5m]))`; compare them with `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{pod=~"catalogue-.*"}[5m])))`. If custom instrumentation exports `mysql_global_status_threads_running`, inspect it; otherwise derive database pressure from catalogue/database structured logs and database-native telemetry
  2. Inspect traces for catalogue spans with high service self-time; if the tracing setup emits database child spans, compare their duration, otherwise correlate catalogue request timing with catalogue-db slow-query evidence. Review `kubectl logs deployment/catalogue -n <namespace> --since=30m` for slow requests and compare controlled request shapes or result sizes without recording sensitive inputs
  3. Run `kubectl top pods -n <namespace> -l name=catalogue --containers` and `kubectl rollout history deployment/catalogue -n <namespace>`. The upstream catalogue binary does not enable a pprof endpoint by default; profile a reproduction in staging with an explicitly instrumented build, or use a separately approved and protected production profiling mechanism rather than assuming `/debug/pprof` exists
- **Remediation & Mitigation**: Immediate — route traffic away from hot pods, rate-limit or disable the proven triggering request shape, and roll back the correlated catalogue build; add known-good replicas only if catalogue-db has capacity. Long-term — optimize the profiled hot path, cap query and result complexity, propagate request deadlines, add worst-case performance tests, size CPU requests and limits from observed demand, and expose guarded profiling only through an approved incident procedure
