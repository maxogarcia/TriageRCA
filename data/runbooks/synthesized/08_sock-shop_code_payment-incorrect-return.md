# Sock Shop Code-Level Faults

## SS-CODE-RET-001: Payment Service Returns an Incorrect Authorization Result
- **Affected Services**: payment, orders
- **Fault Type**: Code-level
- **Symptom**: `POST /paymentAuth` returns HTTP 200 with an `authorised` Boolean that disagrees with the submitted amount and configured decline threshold; orders may continue when an over-threshold amount should be declined or reject an eligible amount. Transport metrics can remain normal because the response is syntactically valid
- **Root Cause**: A defect in payment's amount-threshold comparison or response mapping returns the wrong `authorised` value or message. The Sock Shop payment service makes its decision from `amount` only; it does not validate the supplied card, persist a payment transaction, or return a transaction ID
- **Diagnostic Steps**:
  1. Query `sum by (status_code) (rate(http_request_duration_seconds_count{method="POST",path="/paymentAuth"}[5m]))`; if custom instrumentation exports `sockshop_payment_authorization_result_total`, inspect it; otherwise derive the authorization distribution from the service's structured `method=Authorise result=<bool>` logs
  2. Inspect a redacted trace for the request amount, payment response, and subsequent orders state transition; compare the amount with the payment container's configured `-decline` argument using `kubectl get deployment/payment -n <namespace> -o jsonpath='{.spec.template.spec.containers[?(@.name=="payment")].args}'`, and review `kubectl logs deployment/payment -n <namespace> --since=30m | grep 'method=Authorise'`
  3. Review `kubectl rollout history deployment/payment -n <namespace>` and the running image; from an authorized ephemeral test pod in staging, send boundary amounts immediately below, equal to, and above the configured threshold to `/paymentAuth` and compare the Boolean and message with the expected decision table
- **Remediation & Mitigation**: Immediate — stop or roll back the faulty payment revision, prevent orders with ambiguous authorization results from advancing to shipping, and review affected orders by deployment window, amount, and recorded Boolean result; do not claim capture, refund, or transaction-ID reconciliation because the demo payment service has no such mechanism. Long-term — keep the authorization result typed and explicit, replace floating-point money with validated minor-unit arithmetic if the service is extended, add threshold boundary and contract tests, and add durable audit records and idempotency only when integrating a real payment provider
