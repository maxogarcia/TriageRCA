# Sock Shop Resource Faults

## SS-RES-MEM-002: Carts Service Memory Leak Under Cart Churn
- **Affected Services**: carts
- **Fault Type**: Resource
- **Symptom**: Java carts pod memory grows as carts are created and updated, does not return to its earlier post-GC baseline after load falls, and approaches the container limit; garbage-collection time and HTTP latency increase; the container may be terminated with `OOMKilled`; front-end cart operations may return HTTP 500/503 while carts-db remains reachable
- **Root Cause**: A defect in carts retains cart objects, request buffers, or other per-request state in an unbounded in-process collection, or fails to release resources on update/delete paths. The retained objects survive garbage collection until the JVM heap or container memory limit is exhausted. This diagnosis requires heap evidence; persistent MongoDB documents alone do not constitute a JVM memory leak
- **Diagnostic Steps**:
  1. Compare `container_memory_working_set_bytes{pod=~"carts-.*",container="carts"}`, `jvm_memory_bytes_used{pod=~"carts-.*",area="heap"}`, and `rate(jvm_gc_collection_seconds_sum{pod=~"carts-.*"}[5m])` with `sum(rate(http_request_duration_seconds_count{pod=~"carts-.*"}[5m]))`; a rising post-GC heap baseline after request volume subsides supports retained-memory suspicion
  2. Correlate the growth window with traces for cart add/update/delete paths and inspect current and previous logs using `kubectl logs deployment/carts -n <namespace> --since=1h` and `kubectl logs <carts-pod> -n <namespace> --previous` for `OutOfMemoryError`, GC overhead, or MongoDB resource errors; do not infer the retained type from logs alone
  3. Confirm the termination reason with `kubectl get pod <carts-pod> -n <namespace> -o jsonpath='{.status.containerStatuses[?(@.name=="carts")].lastState.terminated.reason}'` and check live usage with `kubectl top pod <carts-pod> -n <namespace> --containers`; because the carts image is JRE-based, do not assume `jcmd` exists in it—when authorized, attach a compatible JDK ephemeral debug container with `kubectl debug -n <namespace> pod/<carts-pod> -it --image=eclipse-temurin:8-jdk --target=carts`, identify the actual carts Java PID in the shared process namespace, and run `jcmd <java-pid> GC.class_histogram`
- **Remediation & Mitigation**: Immediate — preserve safe heap evidence when feasible, drain and restart the leaking carts pod, roll back the correlated change, and keep traffic on known-good replicas; do not delete carts-db data as a memory workaround. Long-term — fix the confirmed retention path, bound any in-process caches, close MongoDB cursors and other resources, size the JVM heap below the container limit with native-memory headroom, run cart-churn soak tests, and alert on post-GC heap slope plus GC pressure
