# Online Boutique Code-Level Faults

## OB-CODE-PARAM-001: Checkout Sends Incorrect Payment Parameters
- **Affected Services**: checkoutservice, paymentservice, currencyservice
- **Fault Type**: Code-level
- **Symptom**: The amount or currency in checkoutservice's `ChargeRequest` differs from the validated order total. With a valid card, the stock mock paymentservice can still return a transaction ID because it validates card data but does not reconcile the amount with the cart; malformed or invalid card fields instead produce gRPC `INVALID_ARGUMENT`. If custom instrumentation exports `checkout_charge_amount_mismatch_total`, inspect it; otherwise derive the mismatch from redacted structured logs or trace attributes that contain only `Money` fields
- **Root Cause**: checkoutservice maps a stale total, wrong currency code, or incorrectly converted `Money` value into `ChargeRequest` after currency conversion. The protobuf represents money as `currency_code`, `units`, and `nanos`, but the stock paymentservice does not verify that the requested amount equals an independently known order total, so semantically wrong amounts can be accepted rather than rejected
- **Diagnostic Steps**:
  1. If custom instrumentation exports `checkout_charge_amount_mismatch_total`, inspect it; otherwise compare redacted checkout calculation events with payment charge events by trace ID and transaction ID. Separately inspect gRPC status counts for `INVALID_ARGUMENT` only as evidence of card/request validation failures, not proof of an amount mismatch, and correlate changes with `kubectl rollout history deployment/checkoutservice -n <namespace>`
  2. Open an affected trace and compare the cart subtotal, shipping cost, currency conversion outputs, final order total, and `ChargeRequest.amount` (`currency_code`, `units`, `nanos` only); review `kubectl logs deployment/checkoutservice -n <namespace> --since=30m` and paymentservice logs without collecting card numbers, CVV values, or other payment credentials
  3. In a non-production environment, port-forward paymentservice and use a workstation-installed `grpcurl` with the repository's matching protobuf definition and approved synthetic card fixtures to compare a correct and defective request; inspect deployed images with `kubectl get deployment checkoutservice paymentservice -n <namespace> -o jsonpath='{range .items[*]}{.metadata.name}{"="}{.spec.template.spec.containers[0].image}{"\n"}{end}'` rather than assuming diagnostic utilities exist in either application container
- **Remediation & Mitigation**: Immediate — stop or roll back the checkoutservice release that introduced the mapping defect, block further fulfillment when the computed total and charge amount differ, and reconcile affected mock transactions by trace and transaction ID before any controlled retry. Long-term — keep both services on the same versioned protobuf contract, enforce canonical `Money` normalization and currency invariants at checkout, validate the final total immediately before charging, add conversion/rounding and checkout-to-payment contract tests, and alert on explicit amount mismatches separately from `INVALID_ARGUMENT`
