# Online Boutique Code-Level Faults

## OB-CODE-FUNC-002: Checkout Omits the Order Confirmation Call
- **Affected Services**: checkoutservice, emailservice
- **Fault Type**: Code-level
- **Symptom**: Checkout, payment, and shipping complete and `PlaceOrder` can still return success, but the confirmation RPC is absent and the customer receives no confirmation; affected traces finish without an `EmailService/SendOrderConfirmation` span. If custom instrumentation exports `checkout_place_order_success_total` and `email_order_confirmation_requests_total`, inspect their rate gap; otherwise derive the signal from traces and structured checkout/email logs
- **Root Cause**: checkoutservice skips `SendOrderConfirmation` because the call was removed, an early return bypasses it, or a branch suppresses it. In the upstream workflow, confirmation is attempted after the `OrderResult` is built and an email failure is logged without failing `PlaceOrder`, so availability signals can remain healthy even when confirmation is missing
- **Diagnostic Steps**:
  1. Confirm emailservice is ready with `kubectl get pods -n <namespace> -l app=emailservice`; if custom instrumentation exports `checkout_place_order_success_total` and `email_order_confirmation_requests_total`, inspect it; otherwise derive the call-rate gap from structured logs and trace counts, segmented by checkoutservice revision
  2. Compare a healthy and affected trace: both should include successful charge and shipping spans, while the affected trace lacks `EmailService/SendOrderConfirmation`. Review `kubectl logs deployment/checkoutservice -n <namespace> --since=1h` and `kubectl logs deployment/emailservice -n <namespace> --since=1h`; the stock emailservice logs a request for an email address, not an order ID, so use trace context or a controlled test address and redact real customer addresses
  3. Review `kubectl rollout history deployment/checkoutservice -n <namespace>` and the running image; in staging, place one order using a controlled address, verify the trace contains exactly one confirmation RPC, and verify the emailservice log contains one matching controlled-address request—do not claim order-ID log correlation unless custom logging adds it
- **Remediation & Mitigation**: Immediate — roll back or patch checkoutservice to restore the RPC; identify the affected interval from traces and logs, and do not bulk replay confirmations unless an audited deduplication ledger or other verified idempotency control exists, because the stock email RPC has no idempotency key. Long-term — add durable workflow state or an outbox for order-confirmation work, implement explicit deduplication keyed by order ID before enabling replay, add end-to-end post-order assertions, and alert on the checkout-to-confirmation gap
