# Online Boutique Resource Faults

## OB-RES-CPU-001: Frontend CPU Hogging Blocks Request Fan-Out
- **Affected Services**: frontend, cartservice, productcatalogservice, shippingservice, recommendationservice, adservice
- **Fault Type**: Resource
- **Symptom**: Online Boutique pages become slow or return HTTP 502/503/504 responses even though backend services remain healthy; `rate(container_cpu_usage_seconds_total{namespace="<namespace>",pod=~"frontend-.*"}[5m])` approaches the frontend CPU limit; `rate(container_cpu_cfs_throttled_seconds_total{namespace="<namespace>",pod=~"frontend-.*"}[5m])` and frontend p99 HTTP latency rise; traces show delayed or unfinished frontend spans before or during gRPC fan-out to cartservice, productcatalogservice, shippingservice, recommendationservice, and adservice
- **Root Cause**: A tight loop, runaway template or request computation, excessive serialization, or unexpectedly expensive request path consumes the Go frontend container's CPU quota. CPU throttling delays the frontend's HTTP handling and its synchronous gRPC calls, so one saturated frontend pod makes multiple healthy backend dependencies appear slow to users
- **Diagnostic Steps**:
  1. In Prometheus, compare `rate(container_cpu_usage_seconds_total{namespace="<namespace>",pod=~"frontend-.*",container="server"}[5m])` with `kube_pod_container_resource_limits{namespace="<namespace>",pod=~"frontend-.*",container="server",resource="cpu"}` and calculate throttling with `rate(container_cpu_cfs_throttled_periods_total{namespace="<namespace>",pod=~"frontend-.*"}[5m]) / rate(container_cpu_cfs_periods_total{namespace="<namespace>",pod=~"frontend-.*"}[5m])`
  2. Inspect a slow Jaeger trace from the ingress through frontend and compare frontend self-time with the cartservice, productcatalogservice, shippingservice, recommendationservice, and adservice child spans; search frontend logs for the same trace ID and for deadline or context-cancellation errors
  3. Confirm the hot pod with `kubectl top pods -n <namespace> -l app=frontend --containers`; because the frontend image may not include a shell or `top`, use `kubectl debug -n <namespace> pod/<frontend-pod> -it --image=<approved-go-debug-image> --target=server --profile=general` for process inspection, and collect a bounded Go CPU profile only when an authenticated profiling endpoint or approved diagnostic build is enabled
  4. Correlate onset with a release by running `kubectl rollout history deployment/frontend -n <namespace>` and compare CPU across replicas with `kubectl get pods -n <namespace> -l app=frontend -o wide`
- **Remediation & Mitigation**: Immediate — remove the hot pod from traffic, preserve a CPU profile when safe, roll back the correlated frontend revision or disable the triggering route, and scale only known-good replicas after confirming backend capacity. Long-term — profile and bound expensive handlers, add request-size and iteration limits, keep evidence-based CPU requests and limits, add load-regression tests for fan-out routes, and alert on sustained throttling together with frontend p99 latency
