# Sock Shop Resource Faults

## SS-RES-MEM-001: Orders Service Memory Leak
- **Affected Services**: orders
- **Fault Type**: Resource
- **Symptom**: Java orders pod heap and container working set rise across repeated order creation or listing requests, do not return to their previous post-GC baseline after traffic falls, and approach the memory limit; garbage-collection time and order latency increase; the container may be terminated with `OOMKilled` while orders-db and downstream services remain healthy
- **Root Cause**: A defect in orders retains order DTOs, serialization buffers, request state, or other objects beyond their useful lifetime, or fails to release a resource on an order-processing path. The retained objects survive garbage collection until the JVM heap or container memory limit is exhausted. Persistent orders in MongoDB are expected and are not themselves evidence of a JVM leak
- **Diagnostic Steps**:
  1. Compare `container_memory_working_set_bytes{pod=~"orders-.*",container="orders"}`, `jvm_memory_bytes_used{pod=~"orders-.*",area="heap"}`, and `rate(jvm_gc_collection_seconds_sum{pod=~"orders-.*"}[5m])` with `sum(rate(http_request_duration_seconds_count{pod=~"orders-.*"}[5m]))`; verify that the post-GC heap baseline continues rising after request volume returns to normal
  2. Correlate the growth window with traces for create/list order paths and inspect current and previous logs using `kubectl logs deployment/orders -n <namespace> --since=1h` and `kubectl logs <orders-pod> -n <namespace> --previous` for `OutOfMemoryError`, GC overhead, or resource-release errors; compare affected and healthy revisions before naming the retained object
  3. Confirm the termination reason with `kubectl get pod <orders-pod> -n <namespace> -o jsonpath='{.status.containerStatuses[?(@.name=="orders")].lastState.terminated.reason}'` and check live usage with `kubectl top pod <orders-pod> -n <namespace> --containers`; because the orders image is JRE-based, do not assume `jcmd` exists in it—when authorized, attach a compatible JDK ephemeral debug container with `kubectl debug -n <namespace> pod/<orders-pod> -it --image=eclipse-temurin:8-jdk --target=orders`, identify the actual orders Java PID in the shared process namespace, and run `jcmd <java-pid> GC.class_histogram`
- **Remediation & Mitigation**: Immediate — preserve safe heap evidence when feasible, drain and restart the leaking orders pod, roll back the correlated change, and keep traffic on known-good replicas. Long-term — fix the confirmed retention or resource-release defect, bound caches and payload sizes, size the JVM heap below the container limit with native-memory headroom, add repeated-order soak tests, and alert on post-GC heap slope plus GC pressure
